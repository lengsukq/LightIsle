# 性能预算与基准测试

> 这里列的是**目标值与测量方法，不是已验证的实际占用**。必须在 Apple Silicon Mac 上实测整套进程的资源基线。LightIsle 是 SwiftUI Mac 管理端 + 内置 Go Core、独立浏览器中的 Web 与可选 Flutter 用户端；关闭窗口仍在菜单栏运行 NAS，明确退出 App 才停止 Core。UI 视觉效果不能以持续耗电或高内存为代价。

已实施的资源回收和并发保护统一记录在本页。**代码/合成基准通过不等于长期实盘性能达标**；重要数据仍需独立备份。

### 2026-11-03 内存峰值和资源回收

- Web 影院刮削状态轮询同一时间只发一个请求，离页或切换存储时中止旧请求、清除定时器；迟到的响应不会恢复旧页面的轮询。
- Flutter 列表图片离开视口或换图时立即移除待下载请求；已发出的图片下载仍受并发、响应字节和网络超时约束。HTTP 响应声明超过限制时立即取消响应流，不等待下载完整内容。
- 同盘复制和跨盘复制在发布前每批读取最多 128 个目录项，仍按子目录先于父目录的顺序同步落盘。下载完成后的暂存文件检查也分批读取，最多接受 4,096 个文件和 16,384 个目录，超限不发布任何文件。
- 登录后的目录下载和公开文件夹分享共用两个 ZIP 名额，满载时返回可重试的提示；单个文件夹的大小、深度、权限和分享次数限制保持不变。ZIP 写入期限随输出更新，防止长时间停止接收的客户端持续占住名额。

本轮是代码和本地自动化验证；实际大图库、慢速客户端、外接盘和长期驻留时的进程内存曲线仍按 [设备验收](DEVICE_ACCEPTANCE.md) 记录。

### 2026-10-28 后端与原生 Mac 第二轮优化

Apple M4 Pro（Mac16,8）/ 48 GiB / macOS 27.0（26A428）、Go 1.26.1、Swift 6.4；基于 `f32ba89` 及已有未提交开发改动。只用本机工具和合成数据。**B/op 是累计分配，不是存活堆、峰值或进程 RSS；不能以局部比例宣称整个 App 内存降幅。**

| 局部场景 | 原方式 | 新方式 | 测量范围 |
| --- | --- | --- | --- |
| 8 MiB 上传分片 | 约 17,074,410 B/op | 约 74,402 B/op（73 KiB） | 临时 staging 文件，含落盘与 journal 提交；分配减少约 99.6% |
| 单目录 10,000 个文件枚举 | 约 1,010 ms；188,281,909 B/op | 约 27.3 ms；7,160,250 B/op | 旧排序分页遍历与新单次遍历，不含媒体探测/解码/SQLite 写入 |
| 满 50,000 项缓存淘汰一项 | 约 7.87 ms；3,204,520 B/op | 约 0.453 ms；584 B/op | 索引选择/计账，磁盘删除为测试桩，不是真实硬盘删除速度 |
| Mac 状态行解析 | 0.857 秒 | 0.155 秒 | 3 组前后配对的中位数，2,000 条各 32,785 字节，相同 `swiftc -O`；不含 JSON 解码/UI/IPC 等待 |

Go 每组 3 次运行，表格采用代表值（中位数附近）；每次上传/枚举 3 个操作，缓存 20 个操作。并行测试/编译影响耗时，1 万文件旧方式约 0.95–1.67 秒，新方式约 27–28 ms。**上传原方式约 19–21 ms，新方式（含最后 staging 路径身份复核）约 18–24 ms，不能声称吞吐提高**。Swift 解析原方式约 0.846–0.866 秒，新方式约 0.154–0.156 秒；基准核对输出行数与 UTF-8 字节总数，避免只计数而忽略解码结果。

实现与边界：

- 图库/影院使用 `files.Manager.ScanDirectory`，一次遍历、每批最多 200 项；HTTP 排序/游标契约保留。逐批复查根和子目录身份、不跟随链接，回调在管理器锁外执行。取消/换盘/目录替换/读取失败均返回错误，媒体索引不执行完成后的删除清理。
- 上传最多 64 KiB 缓冲，小请求按剩余大小缩小；流式写 staging，先 sync 再推进 journal。断线、超限、剩余大小不符及空间不足回滚已提交前缀；空间检查仍取自打开的 inode、保留 64 MiB 余量。流中 staging 被替换则拒绝提交，回滚不触碰替换文件。
- 单项 LRU 淘汰线性选最旧项，不复制排序全表；相同时间按 key 决定、保护刚发布项。批量字节预算继续排序，删除失败继续计账并反馈错误。
- Mac 状态行分段处理、完整行直接解码；拼接完成/重启/超限后释放缓冲，保留 256 KiB 上限、UTF-8 与 CRLF 规则。隐藏窗口用 `stats summary` 读取主机/卷健康，省去 Mac 进程枚举/传输；开窗保持完整指标。不变的备份/计划/SMB 状态不重复发布 UI 更新。

## 内存生命周期与安全回归（从历史审查归并）

| 资源 | 当前代码策略 | 核心边界 |
| --- | --- | --- |
| 下载引擎 aria2c | 无任务不启动；有活动任务/发布任务阻止退出；空闲连续 5 分钟回收 | RPC 未就绪、进程崩溃或异步提交失败都必须回收句柄并保留可重试状态；暂停/磁力/恢复不丢 journal |
| 多根 Core Runtime | 每分钟检查，根服务空闲 10 分钟且无 HTTP 租约、媒体扫描、备份或 HLS 会话时关闭 | 只释放 SQLite/缓存/任务运行状态，**不删除原片和持久 journal**；重开重新核验 rootID、generation、物理卷 |
| Mac 原生管理窗 | 窗口可见约 3 秒采样；隐藏或轻量模式改 60 秒健康检查并释放重型 UI 清单 | Core、后台上传/任务、原生诊断与尚未保存的草稿继续存在，不能为了省内存杀进程 |
| 缩略图 | 每个根最多 50,000 索引项，目录分批 256 项读取，sidecar 最多 64 KiB | 缓存删除失败不扩张条目，旧数据仍可读；缩略图是派生缓存但原始媒体不能删除 |
| Web/Flutter 查看器 | Web 默认先加载缩略图和 2048 像素预览，缩放/手动请求时读取原片；离页清理回调；Flutter HLS 异步切页前再次检查所属控制器 | 不将浏览器解码堆计入 SwiftUI 宿主 RSS；关闭页面后不可再创建旧播放器 |
| 视频转码 | FFmpeg/HLS 按需会话管理；后台任务持有复制的已打开原片描述符 | 不能直接持有请求即将关闭的 FD，也不能用路径重新打开以绕过原物理身份校验；退出回收句柄与进程 |

**测量口径**：对 SwiftUI 主进程、Go Core、aria2/FFmpeg/Worker、外部 Docker 和浏览器/Flutter **分别**采集 RSS/CPU，并区分累计分配、存活堆与 RSS。可使用 `ps -axo pid,ppid,rss,%cpu,etime,comm`、`vmmap -summary <PID>`、Instruments。需相同机器/图库/并发下至少 3 次测量稳态、峰值、回落与正确性；不以短期合成基准推断节省了多少 MiB。

**禁止的优化**：关闭窗口/锁屏时停止 Go Core 或用户容器；不确定账本直接清零；全局禁止 FSEvents 纠偏扫描；强制周期 GC / FreeOSMemory；对普通 HTTP 或公网开放 heap dump、pprof 或包含私人路径的指标。

仍待实测：1/3/5 根交替访问后的释放、10,000/50,000 张真实照片扫描与解码、100 张大原图浏览器查看、播放器/下载退出后资源回收、连续 24–72 小时 RSS/CPU 曲线，以及完整 Mac 原生页的 Instruments 生命周期。真实设备待办统一见 [设备验收](DEVICE_ACCEPTANCE.md)。

## 1. 资源预算（目标）

| 状态 / 模块 | 初始目标 | 测量口径 |
| --- | --- | --- |
| Go Core 空闲 | 常驻 RSS 50–120 MiB | 启动稳定 10 分钟后进程 RSS |
| SQLite + 小型常驻索引缓存 | 约 10–40 MiB 额外内存预算 | 避免与 Go Core RSS 重复计算 |
| Go 核心 NAS **空闲后台合计** | 力争 100–250 MiB | Go Core + 实际驻留的 LightIsle 媒体进程，**不包含 SwiftUI App、独立 Web 浏览器或 Flutter 客户端** |
| **整套 NAS 宿主空闲总计** | 真机实测后制定基线，不预先承诺 | SwiftUI Mac App + Go Core + 本项目媒体子进程；浏览器与 Flutter 单列，避免混入或遗漏 |
| 空闲 CPU | 在无事件/任务时接近 0，目标平均 <1% 单逻辑核 | 长时间采样并标记单位 |
| 非媒体 API 响应 | 优先 p95 <100ms（局域网、热缓存） | 真机固定样本与负载，记录方法 |
| 图片索引并发 | 初始限 1–2 worker，可配置 | 控制峰值内存与 CPU |
| 视频转码并发 | 开发实现的会话管理器默认最多 2 路（实际随版本核实） | 限制 CPU、内存、磁盘临时缓存；测量硬件解码和软件回退峰值 |
| 缩略图磁盘缓存 | 默认 1 GiB，可在 Mac 管理端调整为 256 MiB–8 GiB，另设每根 50,000 条索引上限 | 可清理重建、保留近期使用；不要把全部缓存算作常驻 RSS |

**以上数字均须实测确认。** 系统级 RSS 与 Swift/FFmpeg 子进程 RSS 的统计应明确且不能遗漏；内存计算避免同一份共享内存重复累加。

不要将 Go 后台资源预算误写为完整的 Mac App 资源预算。**Mac 管理端不内嵌 WKWebView**；用户打开独立浏览器或 Flutter 客户端时单独测量其资源。关闭主窗口后 API 应继续运行；只有明确退出 App 才要求本项目 Core 和监听端口全部释放。

## 2. 必须坚持的性能机制

1. **单 Go 主进程**：认证、文件、图库、影视、任务索引公用服务和 SQLite。
2. **按需媒体处理**：Swift Worker/FFmpeg 有空闲关闭策略，不强制常驻耗资源模型。
3. **批处理 + 增量索引**：FSEvents 为触发，后台定期纠偏；卷离线不全量触发删除。
4. **有界队列**：限定 goroutine / 媒体 worker / 扫描速率 / SQLite 写事务时长。
5. **文件流式 I/O**：下载使用 Range，上传分块校验；不一次读入整部影片或大文件。
6. **响应式页面优化**：照片、文件列表 cursor 分页、虚拟滚动、按需尺寸缩略图。
7. **睡眠友好**：无任务时关闭无意义轮询，硬件监控频率适中，可配置。
8. **缓存独立**：用户业务数据与可删除的缩略图、转码缓存分离，磁盘空间受控。
9. **克制的 iOS 27 风格**：只在导航与重要操作层使用 Liquid Glass；图像网格/文件表格使用不透明或标准材料；Web 限制 backdrop-filter 的面积，减少透明或降低性能时使用不透明回退。
10. **应用生命周期**：只有用户打开 LightIsle.app 时 Go 后端才存活，完全退出后的残留 Go/媒体进程属于性能与功能缺陷。

**Web 按需加载的现有实现（2026-10-25）**：图库与影院组件由 `App.vue` 按需导入，`CinemaView.vue` 在浏览器确实需要 HLS.js 时再动态导入播放器。重构期间主 JavaScript 构建产物由约 904 kB 缩至约 227 kB（不同代码基线及构建环境的静态文件体积比较，**不等于冷启动用时减少相同比例**）。独立 `hls.js` 资源约 593 kB，仍触发 Vite 的 500 kB 分块体积警告，但不阻塞首页；真实网络缓存、首次播放启动时长、内存和 Safari/Android 解码性能仍应实测。

## 4. 质量红线

- 禁止同步全盘扫描阻塞登录和系统 API。
- 禁止 API 接收用户请求后无限制启动 FFmpeg/媒体进程。
- 禁止无限增长的缩略图/转码缓存、任务表和日志。
- 禁止将完整照片/视频载入内存实现简单拷贝。
- 非必要不自动启动 Colima / Docker VM。
- 任何需要常驻 AI 模型的功能必须可单独禁用或不安装。
- 大面积连续毛玻璃、粒子/反光特效不得造成长期 CPU/GPU 负担；低性能/无障碍模式必须关闭动态材质。
- 完全退出 App 后，不允许保留 LightIsle 自有的 NAS HTTP API 及后台工作进程。

# LightIsle 内存占用审查与优化清单

> 代码静态审查：2026-10-27，基于当前 `main` **未提交工作树**。本文是可执行的优化候选清单，**不是**内存泄漏判定、实测报告或已经完成的实现。仅编写文档，本轮不改动运行代码。
>
> 定位：个人 Mac 常驻 NAS。目标是「无人操作时够轻，文件/媒体任务运行时正确」，而不是以停止服务、误清数据、静默中断正在进行的任务换取低 RSS。

## 一、先理解内存从哪里来

| 进程/内存域 | 什么时候存在 | 说明 |
| --- | --- | --- |
| `LightIsle.app`（SwiftUI/AppKit） | App 已打开时 | 管理窗、页面状态、图表、菜单栏；轻量模式卸载窗口 UI，但宿主进程仍存活 |
| `lightisled`（Go Core） | App 正在提供 NAS 时 | HTTP、账号、SQLite、文件服务、媒体索引、后台任务；**轻量模式不能关闭它** |
| `aria2c` | 当前代码中：安装后随 Core 启动 | 下载服务的额外进程；空闲时可考虑按需运行 |
| `lightisle-media-worker` / `ffmpeg` / `ffprobe` | 相关媒体工作发生时 | 各自有单独的瞬时内存峰值，不应算成 Go 的常驻缓存 |
| 独立浏览器的 Vue Web / Flutter Mac 客户端 | 用户另行打开时 | 不在 SwiftUI 宿主内；Web 图片解码或 Flutter 资源不等于 `LightIsle.app` 的 RSS |
| Docker / Colima / 用户外部依赖 | 用户显式运行时 | 外部进程，不能为了降低 LightIsle 占用擅自停止 |

测量必须分别记录进程的 RSS、峰值、CPU、运行场景；需要区分浏览器缓存、共享页面与真正独占的脏页/physical footprint。**不同进程 RSS 相加仅是粗略参考，可能重复计算共享内存。** 现有 [性能预算](PERFORMANCE.md) 的 Go Core 空闲 50–120 MiB、整套后台目标 100–250 MiB 均是**待验收目标**，不能宣传为当前实测值。

## 二、值得优化的地方（按投入回报排序）

### P0-01 · aria2 从「启动 NAS 即常驻」改为「有下载需求时启动」

- **已确认：** `core/cmd/lightisled/main.go` 创建下载管理器后，在检测到 aria2 已安装时直接调用 `downloadCenter.Start()`；`core/internal/downloads/downloads.go` 的 `Start` 启动 `aria2c --enable-rpc`，随后 `pollLoop` 每 **1 秒**查询 SQLite 活动任务。无活跃下载也仍持有子进程和轮询协程。
- **建议：** 默认只打开 SQLite 任务历史，不启动 aria2；新建/继续/重试下载时按需启动。最后一个活跃下载结束、完成发布确认且空闲一段时间（候选 5 分钟）后退出 aria2 并停止其轮询；期间有新任务则取消退出。允许管理员明确设置「下载服务常驻」，但不要默认引入额外配置开关，优先自动管理。
- **必须处理：** queued/running/paused、磁力元数据、任务恢复、完成后的发布与检查、重启报错，以及 `Available()` 当前将「RPC 未运行」视为不可用的语义。不能把「未启动」误报为「未安装」，不能杀掉仍然发布文件的任务；界面显示和 REST 状态需同步调整。
- **预期收益：** 减少无任务时一个 aria2 进程及周期 SQL/RPC 工作；**节省多少 MiB 尚未实测**。
- **验收：** 零任务 10 分钟无 aria2 子进程；新建下载后可自动启动；完成发布后自动退出；暂停/继续/取消/崩溃恢复不丢数据。

### P0-02 · 多硬盘 RootServices 增加闲置释放

- **已确认：** `core/internal/server/root_routing.go` 中 `RootServer.runtimes` 按 rootID 缓存 `rootRuntime`，`runtimeFor` 首次使用后创建；目前仅在相同 ID 代际更换或 `Shutdown` 时关闭，没有空闲到期淘汰逻辑。`core/cmd/lightisled/root_services.go` 每个运行时持有文件管理器、任务 SQLite、图库 SQLite/缓存索引、影院 SQLite/Transcoder。打开过多个物理根后，即使不再访问，也会保留这些对象。
- **建议：** 运行时增加「最后使用时间 + 正在使用的租约/后台任务状态」；例如空闲 10–15 分钟且**无活跃 HTTP、扫描、上传、转码、备份/发布、待确认事务**后安全关闭该根服务。重新访问时按 rootID、generation、物理 Binding 再创建；离线/被移除的根及时释放非活跃缓存。
- **安全约束：** 不允许仅凭计时器在尚有 lease、FSEvents 扫描、文件写入、正在播放的 HLS 会话时关闭。必须解决与现有 `requests.Wait()`、`AcquireRootServices`、`ReconcileRootMedia`、`runtimeFor` 的并发竞争；不得破坏同路径换盘的身份校验。根的**文件**和不可再生数据库绝不因运行时淘汰而删除。
- **预期收益：** 多硬盘频繁切换或历史访问多根后，减少闲置 SQLite 连接、Transcoder sweep 协程、缩略图索引及 Go 对象常驻；单根 NAS 收益可能有限。
- **验收：** 多根交替访问后资源会下降；淘汰与读取/拔盘/换盘/扫描并发测试；恢复访问结果及权限一致。

### P0-03 · 正常模式「关掉管理窗口」仍每 3 秒轮询

- **已确认：** `apps/macos/Sources/LightIsle/AppModel.swift` 的 `beginServicePolling` 为应用生命周期任务；只要不进入轻量模式，关闭正常主窗口仍每 **3 秒**调用 `refreshMetrics()`。本次新增的轻量模式只是在该模式下改为 **60 秒**必要查询；`AppModel` 并不会因为普通关窗自动销毁。
- **建议：** 把「服务级告警/共享卷健康」与「仅管理页面可见时的图表/详细备份/SMB 查询」拆开。无人查看主窗口时停掉 UI 指标采样并丢弃大的页面数据，后台仍保留必要的低频告警；重新显示窗口立即获取一次。是否将普通关窗等同「进入轻量模式」应**另行决定**，先不更改用户已经选择的模式语义。
- **安全约束：** 不降低必须及时处理的错误/磁盘离线通知，不依赖管理界面是否可见来驱动 NAS 任务。
- **验收：** 正常显示窗口有实时图表；只关窗后不再执行 3 秒 UI 采样；锁屏轻量模式、开窗恢复及 Core 异常提示正确。

### P1-04 · 缩略图磁盘缓存索引仍可占用较多 Go 堆内存

- **已确认：** `core/internal/gallery/thumbnail.go` 的 `openThumbnailCache` 对缓存目录 `os.ReadDir`，将全部有效 JPEG/sidecar 信息记录到 `cacheEntries map[string]thumbnailCacheEntry`；`recordThumbnail` 为去重逐项遍历，超预算时的 LRU 淘汰也遍历 map。默认缩略图**磁盘缓存** 1 GiB 是文件体积上限，**不是内存索引对象数上限**。
- **建议：** 先在开发采样中记录每根 `cacheEntries` 条数、Go heap 占用和打开缓存耗时；条目多时再评估按需索引、分批加载、额外的条目数量限制、维护最近使用顺序索引（减少全表查找）。不要直接降到极小磁盘缓存，避免图片反复转码增加内存峰值、CPU 和 I/O。
- **验收：** 1 万/5 万张缩略图样本，启动扫描与运行 heap 有界，LRU/代际身份/缓存完整性测试通过。

### P1-05 · Web 图库查看器不应默认预加载每张原图

- **已确认：** `apps/web/src/PhotosView.vue` 的 `startViewerStages` 在预览图（2048 px）后，对可由浏览器解码的 JPEG/PNG/GIF/WebP **立即执行 `new Image()` 加载原图**；`closeModal` 只是清空选择，当前预加载请求没有明确取消。巨幅照片即使未缩放查看也可能产生浏览器解码内存高峰。
- **建议：** 默认仅加载列表缩略图 + 2048 px 预览；用户选择「原始画质」或放大到需要原图时才请求原图。换图/关窗/卸载时停止不必要的预加载，确保上一张图不会覆盖下一张的状态。大图按可见区域选择合适尺寸，保留查看原件入口。
- **边界：** 这是**浏览器侧**的内存优化，不能作为 macOS 原生宿主内存下降的证据。
- **验收：** 连续查看/关闭 100 张大图的浏览器内存峰值及回落，原图放大、HEIC 不支持时的预览体验不退化。

### P1-06 · 核查重复或不必要的周期媒体扫描峰值

- **已确认：** `core/cmd/lightisled/media_reconciler.go`：旧共享根启动约 30 秒后以及每 **15 分钟**请求媒体对账；`core/cmd/lightisled/root_media_maintenance.go`：多根调度每分钟检查到期、每根约 15 分钟全量对账，且已按根**串行**处理，避免同时扫描全部硬盘。
- **建议：** 区分近期有 FSEvents、目录仍活跃与已稳定的库；先统计真正扫描条目数/耗时/峰值 RSS，再考虑空闲稳定时延长完整纠偏间隔，改用精确的变更批处理和补偿扫描。已变更/离线重连的盘不应被延迟到不可接受。
- **风险：** FSEvents 可能丢事件，不能直接关掉全量纠偏；不要为了省内存牺牲新增文件的发现能力或卷身份安全。
- **验收：** 多盘/上万文件场景，稳定空闲 CPU 和扫描峰值下降，拔盘重连及事件丢失后仍最终一致。

### P1-07 · Mac 管理页面状态再按需分层

- **已确认：** `AppModel.swift` 是生命周期单例，承担大量 `@Published` 状态；`ContentView.swift` 按导航创建不同业务视图。轻量模式已清空 `metrics`、`metricHistory`、备份清单、传输历史和部分检查记录，`metricHistory` 在正常模式已有 **120 条**的限制。
- **建议：** 检查每个「仅详情页使用」的数组、诊断信息及页面 `StateObject` 是否在切页/关闭窗口后仍不必要地保留；只保留正在执行的操作、最后一次简短状态和需要复原的编辑草稿。大清单按分页/需用时读取，避免让常驻单例长期持有完整对象。
- **风险：** 不可清除正在运行的恢复流程、安装任务、关键错误或管理员尚未提交的配置草稿；先用 Instruments 确认可回收对象再改。
- **验收：** 页面来回切换 100 次，内存平台期稳定；重开页面功能与进行中操作状态连续。

### P2-08 · SQLite/Go 堆与并发调参必须以数据为依据

- 多根当前分别创建图库、影院和任务数据库；优先做 P0-02 的生命周期回收。SQLite `SetMaxOpenConns(1)` 已用于部分索引，不应未经压测统一修改缓存 PRAGMA、禁止 WAL 或强制释放页缓存。
- Go 可在**本机仅开发态**采集 `runtime.MemStats` / heap profile，确认实际堆增长点后再评估 `GOMEMLIMIT` 或对象池；不建议定时调用 `runtime.GC()`、`debug.FreeOSMemory()` 以追求看起来更低的 RSS。
- 保证不将 pprof / heap dump 暴露给 LAN、公网或普通用户 API（其中可能包含文件路径、元数据与其他敏感对象）。

## 三、目前已经做对的优化，不要重复开发

| 现有机制 | 代码与判断 |
| --- | --- |
| macOS 原生管理端**不嵌 WKWebView** | `docs/MACOS_APP.md`、`LightIsleApp.swift`；浏览器不应并入原生宿主常驻成本 |
| 轻量模式卸载管理窗视图及部分状态 | `LightIsleApp.swift`、`AppModel.swift`、`LightweightModePolicy.swift`；**实机内存回收幅度待测** |

| 视频转码有会话闲置清理和最大数量限制 | `core/internal/cinema/transcode.go`，音轨探测缓存还设有 **128** 条的防膨胀机制 |
| 缩略图有 256 MiB–8 GiB 的**磁盘容量**限制 | `core/internal/gallery/thumbnail.go`；需要重点补充「内存索引」维度，而非重做磁盘缓存 |
| Web 图库/影院/下载异步载入、离页清理计时器 | `apps/web/src/App.vue`、`PhotosView.vue`、`CinemaView.vue` 等；应优先优化原图加载而非重复做路由懒加载 |

## 四、优化顺序和验收门槛

建议按批次实施，**不要一口气重写 Core 生命周期**：

1. **基线先行（不改行为）**：确认 NAS 空闲 + aria2 已安装情况下的独立进程 RSS、Core heap、root 数量、缩略图索引数、后台唤醒频率；记录 Git HEAD 与外接盘数量。
2. **第一批 / P0**：aria2 按需启停 + 空闲任务关闭；然后多根运行时闲置淘汰。每项单独提交、测试，避免两个生命周期改造相互掩盖问题。
3. **第二批 / P0–P1**：管理窗不可见时降采样；缩略图缓存索引按数量测量并优化。
4. **第三批 / P1–P2**：Web 原图惰性加载、扫描峰值优化、按需释放管理页状态；Go GC/SQLite 参数仅在性能分析证实瓶颈后调整。

### 测试矩阵

| 场景 | 等待与记录 | 必须同时验证 |
| --- | --- | --- |
| Core 冷启动 / 10 分钟空闲 | SwiftUI、Go、aria2、worker RSS；内存占用稳定性 | API、登录、共享卷、磁盘告警工作正常 |
| 正常管理窗 → 仅关闭窗口 | 关闭前、关后 1/10 分钟 | 无 UI 过度轮询，Core 仍能访问 |
| 轻量模式 → 恢复 | 切换前、轻量后 1/10 分钟、恢复后 | 菜单栏 / Dock / 健康状态 / 不重复启动 Core |
| 锁屏 → 解锁（自动开启/关闭两种配置） | 锁屏后、解锁后各 1/10 分钟 | 自定义设置生效、不会自动弹窗或关闭 NAS |
| 连续访问 1/3/5 个硬盘 | 最后访问后 15/30 分钟 | 运行时释放，权限和代际隔离保持 |
| 1 万照片索引与图库缩略图 | 扫描前、扫描峰值、完成 5/30 分钟 | 缩略图正确、缓存大小和内存条目数有界 |
| 影视直放/转码后停止播放 | 播放峰值、停止后 5/15 分钟 | FFmpeg/Worker 退出、不留遗留会话 |
| 下载空闲 → 开始 → 完成/重试 | 三个阶段的 aria2、Go RSS | 状态/历史/发布完整，无丢任务 |
| 连续 24–72 小时无用户操作 | 小时级 RSS 和 CPU 曲线 | 无持续上升趋势、离线卷/自动化/告警有效 |

### 测量口径（Mac 开发机）

- **系统进程表（RSS 单位 KiB）：** `ps -axo pid,ppid,rss,%cpu,etime,comm`，识别 LightIsle、lightisled、aria2c、ffmpeg、Worker。记录采样时间和场景，必要时以活动监视器「内存」交叉验证。
- **独占/共享页：** 对目标 PID 使用 `vmmap -summary <PID>` 或 Instruments 的 Memory Report / Allocations；部分采样需要本机权限与开发签名。Go heap 与进程 RSS 不相等，SQLite/CGImage 及 mmap/文件缓存也会影响进程视图。
- **对比方法：** 同一机型、同样媒体库、相同外部依赖和并发数，对比基线与改造后**空闲稳态**、**峰值**、**回落速度**、CPU、I/O、功能正确性；每项至少 3 次，报告区间而非挑最低一次。
- **不要设置虚假的「优化了 xx MB」数字。** 目前没有录得真实运行态采样；节省量、是否存在真实泄漏、是否达到原有 [PERFORMANCE.md](PERFORMANCE.md) 预算均为**待验证**。

## 五、不得用来省内存的做法

- 不因为锁屏、进入轻量模式、关闭窗口而杀掉 Go Core、FFmpeg 正在执行的转码、正在落盘的传输，或外部 Docker / Colima。
- 不无条件清除应用配置/账号/媒体元数据、暂存上传状态、待确认发布/容量账本；不可再生数据不能和可重建缓存混为一谈。
- 不将离线硬盘视为空盘，不让已淘汰的 RootServices 重连到同路径另一块硬盘。
- 不默认全局禁止缩略图、删除所有索引、强制 GC 或将内存压得过低导致正常使用时频繁抖动。
- 不将浏览器/Flutter 内存变化归功于原生 macOS 主程序；也不只测 `lightisled` 就宣称「整套 NAS」低占用。
